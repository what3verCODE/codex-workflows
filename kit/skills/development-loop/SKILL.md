---
name: development-loop
description: Implement one ticket with scouts, optional diagnosis, oracle, worker or writer, checkpoints and at most two complete review rounds.
---

Accept one ticket identifier and optional instructions, for example `$development-loop https://tracker.example/issues/42 preserve the existing API`. The main agent owns the conversation and transitions. Keep baselines, checkpoints and review count in conversation context only. These are behavioral instructions, not a durable workflow engine or hard runtime/token guarantees.

1. Read `../workflow-context/SKILL.md`. Resolve the ticket body, comments and supplied evidence through available tracker tools and workspace context. Delegate bounded discovery to scouts as needed, including independent filesystem or MCP questions across relevant projects. Read applicable project instructions yourself. Resolve existing edits, branches and original per-repository baselines before implementation.
2. For uncertain bugs, ask bughunter to read `../diagnosing-bugs/SKILL.md` and return evidence and an implementation handoff. Reuse an established cause from the ticket when adequately supported. Standalone diagnosis need not start this loop.
3. Ask oracle to read `../prepared-task/SKILL.md` and assess readiness and approach. Return meaningful unresolved questions to the user and pause dependent work. Accept new user information throughout the run; resume when the required understanding is supplied. Ready work proceeds without a routine approval step.
4. For code behavior changes, worker reads `../tdd/SKILL.md` and performs implementation and available project checks. Documentation-only tasks go to writer with `../workflow-writing/SKILL.md`, without TDD tests. Writer updates affected documentation and memory banks after implementation. The coordinator creates and inspects a checkpoint for each affected repository, following its VCS conventions and preserving unrelated work.
5. Invoke reviewer with `../code-review/SKILL.md`, the task, original baselines and current checkpoints. Every independent specialist analysis belongs to review round one. Both reviews inspect the complete ticket change, including earlier implementation and relevant existing edits.
6. If round one reports blocking defects or clearly actionable in-scope findings, worker corrects code and writer updates affected documentation. Re-run appropriate checks, checkpoint corrections, and invoke reviewer once more against the same original baselines and the new checkpoints. Optional improvements stay separate. If no corrections are needed, finish after round one.
7. Stop after round two and report remaining findings, including blockers. Do not start a third review or automatic third repair pass. If correction is blocked by missing user information, pause dependent work instead of treating time elapsed as an answer.

Return changed behavior and documents, actual automated verification, per-repository baselines and checkpoints, review rounds and outcomes, unresolved findings, unavailable checks and remaining manual UI work. Do not claim acceptance when blockers remain. One invocation owns one ticket; worktrees and parallel terminals remain user-managed. Follow existing personal/workspace policy for publication.

Use named installed roles when available. If a host cannot select a custom role, read its TOML under the workspace `.codex/agents` or global `$CODEX_HOME/agents`, pass `developer_instructions` to a bounded child and apply explicitly configured model/reasoning overrides only through supported spawn parameters. Have the child read the role's required skills. Report that this fallback does not apply role-level sandbox or `skills.config` settings; it inherits the parent environment. If independent agent execution is unavailable, report that review limitation rather than presenting a self-review as independent.
