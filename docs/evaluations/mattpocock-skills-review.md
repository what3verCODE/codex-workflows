## Changes worth preserving

The local [TDD fork](../../kit/skills/tdd/SKILL.md) reuses previously agreed test boundaries. The [review fork](../../kit/skills/code-review/SKILL.md) covers correctness, runtime defects, security and other technical categories, pins the full task change and consolidates evidence-backed findings. Replacing these with upstream would lose deliberate improvements. The local spec/ticket forks also avoid mandatory setup, distinguish drafts from publication and preserve concurrent edits. Their source is already current at the reviewed revision.

Several upstream procedures contain genuine human decision gates. `grilling` waits between rounds and requires final shared-understanding confirmation; `tdd` requires seam agreement; `to-tickets` approves the breakdown; `wizard` confirms the procedure. These explain expected interaction cost. Existing authorization and higher-priority workflow instructions still govern actual use.

## Specific limitations to check before adopting

- The [upstream review](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/code-review/SKILL.md) advertises work-in-progress review but prescribes `git diff <fixed-point>...HEAD`. That command does not include staged or unstaged changes. Your local checkpoint workflow avoids depending on that mismatch.
- The [conflict resolver](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/resolving-merge-conflicts/SKILL.md) says to stage everything and always finish. An adaptation should stage task files only and report unresolved intent instead of forcing a result.
- The [Git hook script](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/misc/git-guardrails-claude-code/scripts/block-dangerous-git.sh) uses literal regular-expression patterns over shell text, without parsing Git options. `git -C repo push` does not match its `git push` check. This is a static inspection finding; no destructive command was run.
- The [wizard template](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/wizard/template.sh) serializes environment values with raw `KEY=VALUE` lines. The generated procedure must handle the target dotenv parser's quoting and multiline rules for its actual values. Hidden terminal input alone does not establish correct storage.
- The [TS boundary template](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/in-progress/setup-ts-deep-modules/dependency-cruiser.config.cjs) has five forbidden-rule entries even though the skill describes four conceptual rules. It enforces import paths and cycles; that does not prove a module's interface is useful or that every runtime dependency is represented.
- The [beta README](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/in-progress/README.md) calls `retro` a nonfunctional stub, while [its SKILL.md](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/in-progress/retro/SKILL.md) contains four executable instruction steps. Treat the maturity label conservatively rather than assuming the procedure is production-tested.
- Some skills literally call a Skill tool, while the local wrappers use file loading when that tool is unavailable. Preserve `agents/openai.yaml` and supporting files during any selective import, and adapt tool calls to this host. A successful file copy is not a runtime compatibility test.

The proposed additions do not require replacing the local `development-loop`, `prepared-task`, `workflow-context` or `workflow-writing`. Those own task execution and project integration. Specialist references should plug into them only when the task calls for that discipline.
